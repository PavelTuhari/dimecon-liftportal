### 1.1. Выполненные работы по развёртыванию

1. Скачан дистрибутив `mysql-8.4.0-winx64.zip` (258 946 761 байт) с официального CDN Oracle.
2. Распакован в `D:\MySQL`; создан конфигурационный файл `my.ini` (utf8mb4, порт 3306, лог ошибок).
3. Инициализирован каталог данных: `mysqld --initialize-insecure` — завершено кодом 0.
4. Сервер запущен как процесс; проверено подключение: `SELECT VERSION()` → `8.4.0`.
5. Создана база `liftportal`, пользователь приложения, выданы права; пароль `root@localhost` установлен (не пустой).
6. В `platform/.env` указан `DATABASE_URL=mysql+pymysql://liftportal:***@127.0.0.1:3306/liftportal?charset=utf8mb4`.
7. Приложение запущено — схема создана автоматически, выполнено заполнение демо-данными.
8. Ранее использовавшийся файл SQLite перенесён в `backup/sqlite-dev/` — подмена источника данных исключена.

`POST /api/v1/quotes` — автокран GROVE GMK 3055, 4 ч, 12 км, стропальщик:

```

Подача техники (зона «Город»)       2 500
Стропальщик                           600
НДС 20 %                            2 380
ИТОГО                              14 280 MDL
```

Проверено: сумма строк соответствует итогу; та же детализация выводится клиенту на сайте и в карточке заказа в кабинете (единая формулировка на всех носителях — требование Тома 2 §2.7). ✅

**Проверка алгоритма подбора.** Сценарий «бытовка 4 т, высота 3 м, машина в 16 м от груза»: расчётная масса с запасом 4,84 т, требуемая высота 10,5 м. Система исключила автокраны 14 т и 17 т (требуемый вылет ≈ 22 м превышает их максимум) и GMK 3055 (на вылете 24 м паспортная грузоподъёмность 4,9 т — запас 1,2 %, ниже нормативных 10 %), выдав GMK 5100. При сокращении расстояния до 10 м подбор выдал два варианта: GMK 3055 «Оптимально» (21 730–29 340 MDL) и GMK 5100 «С запасом» (78 610–106 120 MDL). Поведение соответствует ТЗ. ✅

## 4. Выявленные дефекты и замечания

### Д-1. Двухсекундная задержка ответа по адресу `localhost` — **устранён в ходе испытаний**

| | |
|---|---|
| Критичность | Высокая (влияет на восприятие быстродействия всеми пользователями) |
| Обнаружен | при измерении производительности: все страницы отвечали ровно ≈ 2070 мс независимо от сложности |
| Диагностика | `tools/latency.py`: TCP-соединение к `127.0.0.1` — 0,4 мс, к `localhost` — 2048 мс. `localhost` резолвится сначала в IPv6 `::1`, сервер приложений слушал только IPv4 `0.0.0.0`, клиент ждал таймаут IPv6 и переключался на IPv4 |
| Причина | `waitress.serve(host="0.0.0.0")` — привязка к одному стеку |
| Исправление | `platform/run.py`: `serve(app, listen=f"0.0.0.0:{port} [::]:{port}")` — прослушивание обоих стеков |
| Проверка после исправления | `localhost`: 2072 мс → **28 мс**; повторные измерения раздела 2.5 выполнены после исправления |

### З-1. Письма не отправляются — ожидаемое поведение тестового контура

SMTP не настроен ни у компаний, ни у платформы, поэтому 11 писем зафиксированы в журнале `outbox` со статусом `queued` и пометкой «SMTP не настроен». Письма не теряются, интерфейс кабинета показывает счётчик. Для продуктивной среды требуется указать SMTP компании (экран 36) либо платформы в `.env`. Дефектом не является.

### З-2. Косметика: шкала графика грузоподъёмности

На оси Y используются некруглые деления (110 / 88 / 66 / 44 / 22 т), так как шаг вычисляется от максимума паспортной таблицы. Читаемости не мешает; рекомендуется привести к «круглым» значениям при следующей итерации дизайна.

### З-3. Артефакт автоматической съёмки (не дефект продукта)
