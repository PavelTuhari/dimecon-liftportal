# 1. Общие сведения

## 1.1. Назначение документа

Документ описывает требования к разработке нового веб-решения SA «Dimecon 11» взамен существующего сайта dimecon.md. Решение состоит из трёх логических продуктов в одной кодовой базе:

| № | Продукт | Аудитория | Ключевая задача |
|---|---------|-----------|-----------------|
| A | **Публичный сайт** (marketing site) | все посетители, поисковые системы | продать компанию и услугу, довести до заявки |
| B | **Личный кабинет «Частный клиент»** (B2C) | физлица и микробизнес **без специальных знаний** | самостоятельно подобрать технику и оформить заказ за 3–5 минут |
| C | **Портал партнёра** (B2B) | подрядчики, строительные компании, генподрядчики **со специальными знаниями** | управлять парком арендованной техники по проектам: заявки, графики, смены, документы, акты, счета |

## 1.2. Бизнес-цели

1. Перевести приём заявок из телефона/e-mail в онлайн-канал: **не менее 60 % заявок через сайт к концу 1-го года эксплуатации**.
2. Снизить нагрузку на диспетчера: типовой заказ автокрана до 25 т оформляется клиентом без участия менеджера.
3. Дать генподрядчикам инструмент планирования техники на объекте, который делает Dimecon «системой по умолчанию» и повышает LTV партнёра.
4. Восстановить позиции в органическом поиске по запросам «servicii macara Chișinău», «аренда автокрана Кишинёв», «transport agabaritic Moldova» и т. п.
5. Сделать парк техники (краны, полуприцепы, тралы, самосвалы) публичным конкурентным преимуществом — с грузовысотными характеристиками, графиками загрузки и фотографиями.

## 1.3. Измеримые критерии успеха (KPI, замер через 6 месяцев после запуска)

| Метрика | Текущее (оценочно) | Целевое |
|---|---|---|
| Конверсия «посетитель → заявка» | < 0,5 % | ≥ 3 % |
| Доля заявок, оформленных без звонка | ~0 % | ≥ 40 % |
| Время оформления типового B2C-заказа | 15–40 мин (телефон) | ≤ 5 мин |
| Lighthouse Performance (mobile) | ~25–40 | ≥ 90 |
| Lighthouse Accessibility | не измерялось | ≥ 95 |
| Core Web Vitals LCP (mobile, p75) | > 4 с | ≤ 2,0 с |
| Активные B2B-партнёры с ≥ 1 проектом в портале | 0 | ≥ 25 |
| Повторные заказы B2B через портал | н/д | ≥ 70 % от всех B2B-заказов |

# 2. Аудит текущего сайта (AS-IS)

## 2.1. Что есть сейчас

Обследование dimecon.md (сентябрь 2026):

- **Движок:** самописная PHP-CMS 2010–2012 гг., единая точка входа `index.php` с GET-роутингом вида
  `index.php?pag=page&id=83&l=ro`, `index.php?pag=news&tip=servicii&l=ru`, `?pag=news&opa=view&id=345&tip=auto&l=ro`.
- **Копирайт в подвале:** «© 2012 Dimecon 11 Chişinău».
- **Языки:** RO / RU / EN — переключение через параметр `l=`.
- **Разделы главного меню:** DESPRE NOI / PARCUL DE MACARALE / TRANSPORT / COMANDĂ / SERVICII / RAPOARTE ȘI EVENIMENTE / VÂNZĂRI / CONTACTE.
- **Контент-типы, реально используемые:**
  - `tip=auto` — автокраны (КС-3577 Q=14 т, R=13,0 м, H=14,5 м; КС-4562 Q=17 т; GROVE GMK 5100 Q=100 т, R=46 м, H=68 м);
  - башенные краны (КБ-308/308А, POTAIN MC-85B, CADILLON, IRMAOS TAVARES, COMANSA);
  - гусеничные краны (RDK 250);
  - `tip=transport` — полуприцепы A-441 (10 200 кг), SJ-45S (45 000 кг), CMZAP-93853 (26 000 кг), 3PT 40-206/206M (40 000 кг), FAYMONVILLE SNT-4U (63 000 кг), самосвал 555-102 (10 000 кг);
  - `tip=servicii` — 14 услуг с постраничной навигацией (услуги кранами, перевозка негабарита, монтаж/демонтаж башенных кранов, аренда, проектирование и изготовление элементов связи со зданием, диагностика ГПМ, периодические испытания контрольными грузами, ТО и ремонт ГПМ, ремонт гидрооборудования, перемотка электродвигателей и гидротолкателей и др.);
  - `tip=vinzari` — продажа: стальные канаты Ø 5,6–39,5 мм, грузозахватные приспособления (стропы, чалки, траверсы), аксессуары (крюки, коуши, скобы), оборудование, запчасти для ГПК, аренда помещений;
  - `tip=noutati` — отчёты и события.
- **Каталог PDF:** `/files/files/Catalog_Dimecon.pdf`.
- **Контакты:** тел. +373 22 47 35 32, +373 68 140 336, +373 60 706 604, e-mail office@dimecon.md.
- **Форма заказа:** отдельные «Заказать кран» / «Заказать транспорт» — простая форма обратной связи без расчёта, без подтверждения, без истории.

## 2.2. Выявленные проблемы

**Технические**

1. Нет адаптивной вёрстки — фиксированный макет, на мобильном нечитаемо. Мобильный трафик (≥ 70 % рынка MD) теряется полностью.
2. Отсутствует HTTPS-первичность и современные заголовки безопасности; риски XSS/SQLi в самописной CMS 2012 г. не оценены и не закрыты.
3. URL-структура непригодна для SEO: нет ЧПУ, нет `hreflang`, нет канонических адресов, дубли страниц по языковому параметру.
4. Нет разметки Schema.org (`Organization`, `Product`, `Service`, `LocalBusiness`, `FAQPage`), нет OpenGraph — ссылки в мессенджерах выглядят «пусто».
5. Тяжёлые неоптимизированные изображения, отсутствует lazy-loading, WebP/AVIF, CDN.
6. Контент частично вставлен из Word (артефакты `﻿`, «рваные» пробелы, таблицы вместо разметки), разная типографика в трёх языках.
7. Опечатки в интерфейсе (напр. «КОНТАКТЫTE»), несогласованность переводов между RO/RU/EN, часть контента существует только на одном языке.
8. Стек (PHP 5.x-эры) вне поддержки, обновление безопасности невозможно, разработчик утрачен.

**Продуктовые**

9. Каталог техники — плоский список карточек без фильтров по грузоподъёмности/вылету/высоте, без сравнения, без грузовысотных характеристик в машиночитаемом виде.
10. Невозможно понять **какой кран нужен** — сайт говорит на языке инженера (Q, R, H), а не клиента («поднять бытовку 3 т на 4-й этаж»).
11. Нет цен, нет даже порядка цен и минимальной смены — главный барьер к заявке.
12. Нет доступности техники: клиент не видит, свободен ли кран на нужную дату.
13. Нет личного кабинета, истории заказов, документов, счетов.
14. Нет ничего для постоянных корпоративных клиентов — вся коммуникация в телефоне и WhatsApp, знания не накапливаются в системе.
15. Нет аналитики (нет счётчиков, нет отслеживания конверсий), решения принимаются без данных.

## 2.3. Что переносим в новое решение

Сохраняются и переносятся: вся фактура о компании (основана в 1968 как «ДСМ-11», с 1995 — SA «Dimecon-11»), состав и характеристики парка, перечень 14 услуг, номенклатура раздела «В продаже», архив «Отчёты и события», контакты, PDF-каталог, трёхъязычность RO/RU/EN. Всё остальное (движок, вёрстка, URL, формы) создаётся заново.

# 3. Референсная модель

## 3.1. Что берём у Odoo (industries/construction/general-contractor)

Публичная часть строится по «отраслевой лендинг»-модели Odoo:

- **Герой-блок** с одной чёткой ценностью + двумя CTA: «Рассчитать стоимость» (primary) и «Поговорить с диспетчером» (secondary).
- **Секция «боли отрасли» → «как решаем»**: не перечисление услуг, а перечисление ситуаций заказчика («срочно нужен кран на завтра», «негабарит через весь город», «башенный кран на 8 месяцев стройки», «истёк срок освидетельствования ГПМ»).
- **Модульная сетка возможностей** с иконками и короткими подписями — как «Apps/модули» у Odoo: Краны · Негабарит · Монтаж/демонтаж · Аренда · Диагностика и испытания · ТО и ремонт · Грузозахват · Запчасти.
- **Блок доказательств**: цифры (с 1968 г., 100 т максимум, 60 м вылет, > 100 м высота, N единиц техники, N проектов/год), логотипы брендов парка (POTAIN, COMANSA, CADILLON, IRMAOS TAVARES, GROVE), кейсы с фото.
- **Прозрачная «тарифная» секция** — минимальная смена, подача, часовая ставка «от», что входит в цену; без скрытых условий (аналог pricing-блока Odoo).
- **Плотный FAQ** с микроразметкой `FAQPage`.
- **Sticky-CTA** и повторяющиеся точки входа в калькулятор по всей длине страницы.
- **Видео/скриншот-демо портала** для B2B-аудитории.

## 3.2. Что берём у Fieldwire (app.fieldwire.com)

B2B-портал строится как рабочий инструмент прораба/снабженца на объекте:

- **Сущность верхнего уровня — Проект (объект строительства)**, а не заказ. Всё внутри проекта: заявки, техника, смены, документы, люди, фото.
- **Задачи/заявки со статусной моделью** и канбан/список/календарь — три представления одних данных.
- **План объекта с пин-метками**: загрузка PDF/DWG-подложки или спутникового снимка, расстановка меток «точка стоянки крана», «зона разгрузки», «ЛЭП», «въезд»; метка связана с заявкой.
- **Фото-документирование**: фото с привязкой к смене/заявке, с датой, автором и геометкой; лента активности проекта.
- **Календарь/график техники** (Gantt-подобный) — какая единица техники когда на объекте, кто оператор.
- **Роли и права** на уровне проекта (владелец, прораб, снабженец, наблюдатель).
- **Мобильный сценарий и офлайн**: PWA, работа на объекте при слабом интернете, отложенная синхронизация фото и отметок.
- **Отчёты и экспорт**: сменный рапорт, табель часов, акт выполненных работ — в PDF/XLSX одним нажатием.

## 3.3. Чего сознательно НЕ делаем

- Не строим полноценную ERP/CRM внутри сайта — бэкофис интегрируется с существующей учётной системой (1С / контур учёта), портал не является системой бухучёта.
- Не делаем «маркетплейс» с чужой техникой на первом этапе.
- Не делаем онлайн-оплату для B2B (там — счета и отсрочка); онлайн-оплата только в B2C.

# 5. Архитектура и технологический стек

## 5.1. Стек

**Backend**
- Python 3.12+
- Flask 3.x (application factory + Blueprints)
- SQLAlchemy 2.x (declarative, typed) + Alembic (миграции)
- PostgreSQL 16 + расширения `pg_trgm` (поиск), `PostGIS` (гео: адреса объектов, зоны выезда)
- Redis 7 — кэш, сессии, брокер очередей, rate-limit
- Celery 5 — фоновые задачи (письма, SMS, генерация PDF, синхронизация с 1С, пересчёт доступности техники)
- Flask-Login + Flask-WTF (CSRF) + Flask-Limiter + Flask-Talisman (CSP/HSTS)
- Flask-Babel — локализация RO/RU/EN
- Flask-Migrate, Flask-Caching, Flask-Mail (или напрямую SMTP-клиент через Celery)
- marshmallow / pydantic v2 — валидация и сериализация API
- WeasyPrint — генерация PDF (КП, акты, сменные рапорты, счета)
- boto3 — объектное хранилище (S3-совместимое: MinIO / Cloudflare R2)

**Frontend**
- Jinja2 + **HTMX** + **Alpine.js** — server-driven UI без SPA-фреймворка для публичной части и B2C
- Tailwind CSS 3.x + собственный дизайн-токен-слой; сборка через Vite
- Для B2B-портала: те же Jinja+HTMX, плюс точечные «острова» на Vanilla/Alpine для тяжёлых виджетов:
  - календарь-график техники (`vis-timeline` или `FullCalendar` resource-timeline),
  - просмотр планов объекта с пинами (`OpenSeadragon` / `pdf.js` + слой меток),
  - карта (`MapLibre GL` + OpenStreetMap-тайлы либо `Leaflet`)
- PWA: manifest + Service Worker (Workbox) — офлайн-кэш планов, очередь отложенной отправки фото и отметок

**Инфраструктура**
- Docker + docker-compose (dev) / Docker Swarm или Kubernetes (prod, по выбору хостинга)
- Gunicorn (gevent/uvicorn-worker) за Nginx
- Хранение файлов — S3-совместимое, не на диске приложения
- Sentry — ошибки; Prometheus + Grafana — метрики; Loki — логи
- CI/CD — GitHub Actions / GitLab CI

**Обоснование выбора HTMX вместо SPA:** публичная часть должна быть максимально индексируемой и быстрой (LCP ≤ 2 с на мобильном 4G), а B2B-портал — предсказуемым и дешёвым в поддержке для небольшой команды. Server-rendered + HTMX даёт SEO, скорость первой отрисовки и одну кодовую базу шаблонов вместо двух.

## 5.3. Ключевые архитектурные правила

1. **Толстый сервисный слой, тонкие вью.** Любая бизнес-формула (стоимость, подбор, доступность) живёт только в `app/services/` и покрыта unit-тестами.
2. **Никакой бизнес-логики в шаблонах.** Jinja — только отображение.
3. **Идемпотентность** операций создания заказа/заявки (ключ идемпотентности в форме и в API).
4. **Все внешние вызовы** (SMS, платежи, 1С) — через Celery с ретраями и circuit breaker; UI никогда не ждёт внешний сервис синхронно.
5. **Аудит-лог** на все изменения бизнес-сущностей (кто, что, когда, было → стало), неизменяемая таблица `audit_log`.
6. **Feature flags** для поэтапного включения модулей портала.

## 7.2. B2C: раздел для физических лиц (модуль B)

> **Главный принцип раздела: клиент не обязан знать ни одного технического термина.** Все инженерные величины (вылет, грузовысотная характеристика, схема запасовки) система выводит сама из бытовых ответов.

### 7.2.1. Подборщик-визард «Что вам нужно поднять?»

Пошаговая форма, один вопрос на экран, прогресс-бар, возможность вернуться, автосохранение в сессию, восстановление по ссылке.

**Шаг 1. Тип задачи** — крупные карточки с иконками и бытовыми формулировками:
- «Поднять что-то тяжёлое на высоту» (стройматериалы, оборудование, бытовка, ёмкость, мебель на верхний этаж)
- «Установить/снять оборудование» (кондиционер, антенна, реклама, генератор, котёл)
- «Перевезти крупный или тяжёлый груз»
- «Разгрузить фуру / доставить и разгрузить»
- «Установить забор, столбы, опоры, памятник»
- «Другое / не знаю» → короткая форма + обратный звонок

**Шаг 2. Что за груз.** Выбор из пресетов с уже зашитым весом и подсказкой-картинкой:
| Пресет | Типовой вес | Подсказка |
|---|---|---|
| Бытовка / вагончик 6 м | 2,5–3,5 т | «обычно 3 т» |
| Ёмкость / бак 5 м³ | 1,5 т | |
| Кондиционер промышленный | 0,3–1,2 т | |
| Поддон кирпича / блоков | 1,2–1,8 т | |
| Металлоконструкция / ферма | по вводу | |
| Автомобиль | 1,2–3 т | |
| Септик / бассейн | 1–4 т | |
| Не знаю | → помощник оценки: габариты + материал → оценка массы |

Обязательно: **калькулятор массы по объёму и материалу** (бетон 2,4 т/м³, сталь 7,85, кирпич 1,8, вода 1,0 и т. д.) для тех, кто не знает вес.

**Шаг 3. Куда поднимаем.** «На какой этаж / какая высота?» — слайдер с подписями «1-й этаж ≈ 3 м», «5-й этаж ≈ 15 м», «на крышу 9-этажки ≈ 28 м». Плюс переключатель «указать в метрах».

**Шаг 4. Где стоит кран.** Ключевой для вылета вопрос, заданный по-человечески: «Насколько далеко машина сможет подъехать к месту подъёма?» — варианты: «вплотную (до 5 м)», «через тротуар/газон (5–12 м)», «через дом/забор (12–25 м)», «больше 25 м / не знаю» + возможность указать на карте две точки (стоянка и груз) — расстояние считается автоматически.

**Шаг 5. Условия.** Чекбоксы с пояснениями-тултипами: провода/ЛЭП рядом · работа в выходной или ночью · нужен стропальщик · нужно разрешение на занятие проезжей части · узкий двор · мягкий грунт · охраняемая территория/пропуск.

**Шаг 6. Когда и где.** Дата и временной интервал, длительность (с подсказкой «минимальная смена — N часов»), адрес с автодополнением и картой.

**Шаг 7. Результат** — экран рекомендации (см. 7.2.2).

**Шаг 8. Контакты и подтверждение** — имя, телефон (с верификацией по SMS-коду), e-mail, комментарий; оформление без обязательной регистрации — аккаунт создаётся автоматически по номеру телефона, пароль задаётся позже по ссылке.

### 7.2.2. Алгоритм подбора (`services/crane_selector.py`)

Входные данные визарда преобразуются в инженерные параметры:

```
m_load      = масса груза, т (из пресета или ввода)
m_rig       = масса грузозахвата (стропы/траверса), т  (по умолчанию 0,1·m_load, минимум 0,05 т)
m_calc      = (m_load + m_rig) × K_safety            , K_safety = 1,10 (запас 10 %)
H_req       = H_подъёма + h_груза + h_строп + запас 2,0 м над препятствием
R_req       = L_отступ + 0,5·габарит_груза + R_база  , R_база = габарит выносных опор /2
```

Далее по таблице `equipment_load_charts` для каждой единицы техники ищется конфигурация, где
`radius_m ≥ R_req` **и** `capacity_t ≥ m_calc` **и** `height_m ≥ H_req`, с учётом типа опор.
Результат ранжируется: (1) минимальная достаточная машина по стоимости смены; (2) запас по грузоподъёмности не менее 10 % и не более 300 % (иначе клиент переплачивает); (3) доступность на запрошенную дату; (4) минимальное плечо подачи от базы.

**Выдаются три варианта:** «Оптимально» (подсвечен), «Дешевле» (если есть компромисс), «С запасом» (если условия на объекте могут отличаться от заявленных).

**Обязательный дисклеймер** на экране результата: подбор предварительный, окончательная схема производства работ и допустимость подъёма определяются ИТР Dimecon после уточнения условий на площадке; при опасных сближениях (ЛЭП, стеснённые условия) требуется ППР и согласование. Система **не имеет права** выдавать результат как окончательный инженерный расчёт — это требование безопасности и юридической защиты.

**Автоматическая эскалация к человеку** (визард не даёт самостоятельно оформить, а переводит на диспетчера), если: масса > 60 % от максимума парка; работа рядом с ЛЭП; высота > 40 м; ночные работы; груз «не знаю»; требуется перекрытие улицы; объект вне зоны обслуживания.

### 7.2.3. Калькулятор стоимости (`services/pricing.py`)

```
Итого = Подача (мобилизация)
      + max(часы_факт, мин_смена) × ставка_час × коэф_время
      + доп. услуги (стропальщик, траверса, согласование)
      + перепробег (км сверх бесплатной зоны × тариф_км)
      + надбавка за условия (ночь / выходной / праздник / зима)
      − скидка
      + НДС 20 %
```

Показывается **вилка** («ориентировочно 4 800–6 200 MDL»), а не единственное число, с раскрывающейся детализацией по строкам и явным указанием, что входит и что не входит. Точная цена фиксируется в КП после подтверждения диспетчером.

### 7.2.4. Оформление заказа и оплата

- Проверка доступности выбранной единицы в реальном времени; при занятости — предложение ближайшего свободного слота или альтернативной машины.
- **Мягкое бронирование** слота на 2 часа с момента отправки заявки (`equipment_availability` с `reason=reserve`), затем автоснятие.
- Подтверждение по SMS + e-mail с номером заказа и ссылкой отслеживания (доступна и без входа по подписанному токену).
- Оплата: предоплата/аванс (настраиваемый %) картой через платёжный шлюз MD (Paynet / maib ecommerce / MIA instant payments) либо «оплата по счёту»/наличными водителю. Хранение карточных данных на стороне сайта запрещено — только редирект/iframe шлюза, PCI-DSS SAQ-A.
- Автоматический документ: подтверждение заказа (PDF) и, после выполнения, акт + фискальный чек/счёт.

### 7.2.5. Личный кабинет частного клиента

- Мои заказы (активные / история) со статусами и таймлайном.
- Отслеживание: «техника выехала», ETA, телефон водителя (открывается за 1 ч до подачи).
- Документы: счета, акты, чеки — скачать PDF.
- Повтор заказа в один клик («Заказать так же»).
- Оценка выполненной работы (1–5 + комментарий) → используется в публичных отзывах после модерации.
- Адреса, сохранённые объекты, профиль, язык, согласия на маркетинг.

### 7.2.6. Требования доступности B2C-раздела

- Весь визард проходится с клавиатуры и с экранного диктора (WCAG 2.2 AA).
- Размер тач-таргета ≥ 44×44 px, шрифт основного текста ≥ 16 px.
- Формы устойчивы к вводу телефона в любом формате (`+373`, `0`, пробелы, дефисы) — нормализация на сервере.
- Ни один шаг не требует ввода более 3 полей.
- Полная работоспособность на мобильном в вертикальной ориентации.

## 7.3. B2B: портал партнёра (модуль C)

> Аудитория — прорабы, снабженцы, руководители участков. Они **знают** термины, им нужна скорость, повторяемость и документы. Модель — Fieldwire.

### 7.3.1. Онбординг партнёра

1. Заявка на подключение с сайта (`/parteneri`): компания, IDNO, контактное лицо, сфера, объём потребности.
2. Менеджер Dimecon верифицирует, заводит `partner`, назначает прайс-лист, лимит, отсрочку.
3. Партнёр получает инвайт → задаёт пароль → приглашает своих сотрудников (по e-mail, с ролью).
4. Загрузка реквизитов и подписанного договора в раздел «Документы».

### 7.3.2. Рабочее пространство

Левая навигация (постоянная): **Проекты · Заявки · График техники · Смены · Документы · Счета · Команда · Каталог · Настройки**.

**Проекты (объекты).** Список/карточки: название, адрес, период, статус, активная техника сейчас, открытые заявки, расход за месяц. Внутри проекта — вкладки:

1. **Обзор** — сводка, лента активности (кто что сделал), ближайшие подачи, KPI (часы за месяц, простои, сумма).
2. **Заявки (задачи)** — три представления: список (плотная таблица с фильтрами), канбан по статусам, календарь. Быстрое создание заявки за ≤ 30 секунд из шаблона («как в прошлый раз»), массовое создание повторяющихся заявок (напр. «кран каждый вторник в 8:00 в течение 6 недель»).
3. **План объекта** — загрузка PDF/изображения, зум/пан, расстановка пинов (стоянка крана, зона складирования, ЛЭП, въезд, точка подъёма). Пин связывается с заявкой: диспетчер и крановщик видят, куда ехать и где встать. Версионирование планов.
4. **График техники** — timeline-диаграмма: строки = единицы техники, столбцы = дни/часы; видно подтверждённые брони, заявленные, конфликты. Drag-and-drop только для запроса переноса (окончательное решение — за диспетчером).
5. **Смены** — сменные рапорты по дням: фактические часы, простои, число подъёмов, фото, подписи. Прораб подтверждает или оспаривает рапорт прямо в портале (аналог верификации задач в Fieldwire).
6. **Файлы** — документы проекта, ППР, схемы строповки, разрешения, фотоархив.
7. **Команда проекта** — участники и права, контакты экипажей Dimecon на объекте.

**Сквозные разделы**

- **Счета и баланс**: выставленные счета, оплаченные/просроченные, остаток кредитного лимита, экспорт для бухгалтерии, интеграция с e-Factura (MD).
- **Договорные тарифы**: партнёр видит свой прайс-лист — ставки, минимальная смена, подача, коэффициенты. Прозрачность вместо «звоните, уточним».
- **Каталог с доступностью**: тот же парк, но с реальным календарём занятости и договорной ценой вместо «от».
- **Аналитика партнёра**: расходы по проектам и месяцам, структура (техника/услуги/перепробег), простои и их причины, сравнение периодов; экспорт XLSX/CSV.

### 7.3.3. Мобильный сценарий и офлайн (PWA)

- Установка на домашний экран, брендированный splash.
- Экран «Сегодня»: что подаётся сегодня, кто оператор, кнопка «Позвонить водителю», «Подтвердить смену», «Добавить фото».
- Офлайн: кэшируются планы объекта, открытые заявки, черновики рапортов; фото и отметки ставятся в очередь и синхронизируются при появлении сети. Конфликты разрешаются по правилу «сервер побеждает, локальная версия сохраняется как черновик с уведомлением».
- Push-уведомления (Web Push): техника выехала, смена требует подтверждения, счёт просрочен, заявка подтверждена/отклонена.

### 7.3.4. Уведомления партнёра

Настраиваемые по каналам (in-app / e-mail / Web Push / Telegram / SMS для критичных) и по событиям: заявка принята, назначена техника, изменено время подачи, техника выехала, смена закрыта, рапорт ждёт подтверждения, счёт выставлен, счёт просрочен, срок договора/лимит.

### 7.3.5. API для партнёров

REST API v1 (OpenAPI 3.1, аутентификация по API-ключу + HMAC-подписи или OAuth2 client_credentials, rate-limit по партнёру):

```
GET    /api/v1/equipment                    каталог с ТТХ
GET    /api/v1/equipment/{id}/availability  занятость на период
POST   /api/v1/quotes                       предварительный расчёт
GET    /api/v1/projects                     проекты партнёра
POST   /api/v1/projects/{id}/orders         создать заявку
GET    /api/v1/orders/{id}                  статус заказа
GET    /api/v1/shifts?from=&to=             сменные рапорты
GET    /api/v1/invoices                     счета
POST   /api/v1/webhooks                     подписка на события
```

Webhook-события: `order.confirmed`, `order.scheduled`, `equipment.dispatched`, `shift.submitted`, `invoice.issued`, `invoice.overdue`.

Не является отдельным продуктом для клиента, но **обязателен**, иначе портал не работает.

Карточки техники, ТТХ и грузовые характеристики (импорт таблиц из CSV/паспортов), документы и сроки освидетельствования с алертами, наработка, план и история ТО, простои и причины, расход топлива, фотофиксация состояния.

### 7.4.5. Контент и SEO

CRUD страниц, услуг, товаров, новостей, кейсов с полями на трёх языках бок о бок и индикатором незаполненных переводов; медиатека с автогенерацией WebP/AVIF и alt-текстов; редактор SEO-полей и OG-превью; управление редиректами; предпросмотр перед публикацией.

# 8. Мультиязычность

1. Языки: **ro** (по умолчанию), **ru**, **en**. Архитектура допускает добавление языка без изменения схемы БД.
2. Интерфейс — Flask-Babel (`.po`/`.mo`), контент — JSONB-поля `*_i18n` в моделях.
3. URL: языковой префикс `/<lang>/<slug>`; слаг переводится (`/ro/servicii-cu-macarale`, `/ru/uslugi-kranami`, `/en/crane-services`), 301 со старого слага при изменении.
4. `<link rel="alternate" hreflang="...">` для всех языковых версий + `x-default`.
5. Определение языка: URL → cookie → `Accept-Language` → ro.
6. Форматы: даты `dd.MM.yyyy`, валюта `MDL` (`1 234,50 lei`), десятичный разделитель — запятая, единицы измерения локализованы.
7. Переключение языка сохраняет текущую страницу (а не бросает на главную) — при наличии перевода; иначе ведёт на языковую главную с уведомлением.
8. Рабочий процесс перевода: выгрузка непереведённых строк в XLSX → перевод → загрузка обратно.

# 10. Нефункциональные требования

## 10.1. Производительность

- TTFB ≤ 200 мс (кэшируемые публичные страницы), ≤ 500 мс (персонализированные).
- LCP ≤ 2,0 с (mobile, 4G, p75), CLS ≤ 0,05, INP ≤ 200 мс.
- Вес первой загрузки публичной страницы ≤ 250 КБ (без изображений), критический CSS инлайн.
- Изображения — AVIF/WebP, `srcset`, lazy-loading, CDN.
- Кэширование: Redis для каталога и справочников, HTTP-кэш с ETag, инвалидация по событиям публикации.
- Выдерживает 200 одновременных пользователей и 50 RPS без деградации; нагрузочный тест (Locust) — часть приёмки.

## 10.2. Безопасность

- HTTPS-only, HSTS с preload, TLS 1.3, редирект 301 с http и с www (или наоборот — выбрать канонический хост).
- CSP без `unsafe-inline` (nonce для скриптов), `X-Content-Type-Options`, `Referrer-Policy`, `Permissions-Policy`, `X-Frame-Options`/`frame-ancestors`.
- CSRF на всех формах (Flask-WTF), SameSite=Lax/Strict-cookies, `HttpOnly`, `Secure`.
- Пароли — argon2id; 2FA (TOTP) обязательна для всех ролей бэкофиса и доступна партнёрам.
- Rate-limit: вход (5/мин на IP+логин), SMS-коды (3/час на номер), формы (10/час на IP), API (по ключу).
- Только параметризованные запросы (ORM); запрет сырых SQL-строк с конкатенацией — проверяется линтером.
- Загрузка файлов: белый список MIME и расширений, проверка магических байтов, лимит размера, антивирус (ClamAV) для B2B-вложений, отдача из S3 через подписанные ссылки с TTL, никогда не из статики приложения.
- Изоляция арендаторов B2B — обязательная фильтрация по `partner_id`, покрытая отдельными интеграционными тестами «пользователь A не видит данные B».
- Секреты — только в переменных окружения/секрет-хранилище, ни одного в репозитории; ротация ключей.
- Логирование доступа к персональным данным; аудит действий бэкофиса.
- Ежедневные бэкапы БД (RPO ≤ 24 ч, для транзакционных данных — WAL-архивирование, RPO ≤ 15 мин), проверка восстановления ежеквартально, RTO ≤ 4 ч.
- Перед запуском — внешний pentest/OWASP ASVS L2 чек-лист.

## 10.3. Приватность и соответствие

- Соответствие Закону РМ № 133/2011 о защите персональных данных и GDPR (для EU-посетителей).
- Cookie-баннер с реальным выбором (по умолчанию — только необходимые), журнал согласий.
- Политика конфиденциальности, оферта, условия аренды — на трёх языках.
- Экспорт и удаление персональных данных по запросу пользователя (в ЛК).
- Сроки хранения: лиды — 24 мес., заказы и документы — по закону о бухучёте, логи — 12 мес.

## 10.4. Доступность

WCAG 2.2 уровень AA: контраст ≥ 4,5:1, семантическая разметка, `alt` у всех содержательных изображений, видимый фокус, skip-link, корректные `label`/`aria`, отсутствие «ловушек» фокуса, работоспособность при 200 % масштабе. Проверка axe-core в CI + ручная проверка клавиатурой и NVDA.

## 10.5. SEO

- ЧПУ, уникальные `title`/`description` для каждой страницы и языка, автогенерация с возможностью переопределения.
- `sitemap.xml` (с индексом и языковыми альтернативами), `robots.txt`, `feed.xml`.
- Schema.org: `Organization` + `LocalBusiness` (с `openingHours`, `geo`, `telephone`), `Service`, `Product`, `BreadcrumbList`, `FAQPage`, `Article`, `AggregateRating` (после накопления отзывов).
- Хлебные крошки на всех вложенных страницах.
- 301-редиректы со всех старых URL (§13).
- Отдельные посадочные страницы под ключевые запросы и города: Кишинёв, Бельцы, Кагул, Унгень, Комрат (шаблон «услуга + город», с уникальным контентом, не дорвеи).

Chrome/Edge/Firefox/Safari — 2 последние мажорные версии; iOS Safari 15+; Android Chrome 100+. Деградация без JS: публичный сайт и формы заявки должны работать (progressive enhancement); портал может требовать JS.

## 10.7. Наблюдаемость

Структурированные JSON-логи с `request_id`; метрики Prometheus (латентность, ошибки, очередь Celery, конверсия визарда по шагам); алерты в Telegram/e-mail при 5xx > 1 %, недоступности платёжного шлюза, росте очереди задач; аптайм-мониторинг внешним сервисом; SLA доступности 99,5 %.

# 12. API и интеграционные контракты

- Спецификация OpenAPI 3.1 в `docs/openapi.yaml`, публикуется как интерактивная документация на `/api/docs` (только для авторизованных партнёров).
- Версионирование в пути (`/api/v1/`), обратная совместимость в пределах мажорной версии, депрекация с уведомлением за 6 месяцев.
- Формат ошибок — RFC 9457 (`application/problem+json`).
- Пагинация — курсорная (`?cursor=&limit=`), лимит по умолчанию 50, максимум 200.
- Все даты — ISO 8601 с таймзоной; внутреннее хранение в UTC, отображение в `Europe/Chisinau`.
- Идемпотентность POST — заголовок `Idempotency-Key`.
- Rate-limit — заголовки `RateLimit-*`.

# 13. Миграция данных и контента

1. **Инвентаризация:** выгрузка всех страниц старого сайта (краулинг + доступ к БД старой CMS), составление реестра URL → новый URL.
2. **Контент:** перенос текстов о компании, 14 услуг, карточек техники, транспорта, товаров раздела «В продаже», архива «Отчёты и события», PDF-каталога. Тексты проходят редактуру и сверку трёх языков.
3. **Техника:** ТТХ переносятся в типизированные поля; **грузовые характеристики оцифровываются из паспортов** (важный, трудоёмкий и обязательный этап — без них не работает подборщик). Ответственность за предоставление паспортов — на заказчике; формат приёмки — заполненные CSV-шаблоны, подписанные главным инженером.
4. **Медиа:** все фото переснимаются/переобрабатываются (минимум 6 качественных фото на единицу техники, включая фото на объекте), оптимизируются, получают `alt` на трёх языках.
5. **Редиректы:** карта 301 со всех старых адресов вида `index.php?pag=…` на новые ЧПУ (через таблицу `redirects` + правило в Nginx); несуществующие — на тематический раздел, не на главную. Сохранение старых адресов в `robots.txt` не блокируется до переиндексации.
6. **Клиенты:** если существует база контактов/заказов — импорт контрагентов и истории (CSV/1С), с получением согласий на коммуникацию.
7. **Проверка после запуска:** сверка индексации в Search Console, контроль 404, мониторинг позиций 8 недель.

# 14. Качество, тестирование, процессы разработки

## 14.1. Тестирование

| Уровень | Инструмент | Требование покрытия |
|---|---|---|
| Unit (сервисы: подбор, цена, доступность, статусы) | pytest | ≥ 90 % по `app/services` |
| Интеграционные (БД, репозитории, права, изоляция партнёров) | pytest + testcontainers | ≥ 80 % |
| API-контракты | schemathesis по OpenAPI | все эндпоинты |
| E2E (визард, заказ, оплата-sandbox, портал) | Playwright | 20+ ключевых сценариев |
| Доступность | axe-core в CI | 0 критичных нарушений |
| Производительность | Lighthouse CI + Locust | пороги из §10.1 |
| Безопасность | bandit, pip-audit, OWASP ZAP baseline | 0 high/critical |

Обязательные негативные тесты: двойное бронирование одной единицы техники на пересекающийся интервал; доступ партнёра A к проекту партнёра B; недопустимый переход статуса заказа; повторная отправка платёжного вебхука (идемпотентность).

## 14.2. CI/CD

Pipeline: линт (ruff, black, mypy) → тесты → сборка образа → деплой на staging → smoke-тесты → ручное одобрение → prod (blue-green или rolling). Миграции — отдельным шагом, обратно совместимые (expand/contract), откат по плану.

## 14.3. Среды

`local` (docker-compose, seed-данные) · `staging` (полная копия, закрыта basic-auth и `noindex`) · `production`.

## 14.4. Стандарты кода

PEP 8 + ruff (строгий профиль), полные type hints и mypy в strict для `services` и `models`, докстринги для публичных функций, conventional commits, обязательный code review, ADR для значимых решений в `docs/adr/`. Кастомное правило линтера: запрет `Model.query` вне `repositories/`.

## 14.5. Документация к сдаче

- README (запуск за 10 минут), документация API, схема БД (ERD), руководство администратора/контент-менеджера (RU + RO), руководство партнёра, runbook инцидентов, план восстановления, ADR-журнал, видеоинструкции (5–7 коротких роликов) для бэкофиса и партнёров.

| Риск | Влияние | Митигация |
|---|---|---|
| Грузовые характеристики техники не оцифрованы / паспорта утеряны | высокое — не работает ядро подборщика | этап 0: инвентаризация паспортов; при отсутствии — консервативные таблицы от производителя или ручной режим «по запросу» для конкретной единицы |
| Неверный подбор → инцидент на объекте | критическое (безопасность, ответственность) | дисклеймер, запас 10 %, обязательная верификация ИТР перед подтверждением, автоэскалация в «серых» случаях, журнал всех выданных рекомендаций |
| Сопротивление диспетчеров («привычнее по телефону») | среднее | вовлечение в дизайн, обучение, бонус за онлайн-заказы, телефон остаётся как канал |
| Партнёры не начнут пользоваться порталом | высокое для модуля C | пилот с 3–5 лояльными партнёрами до масштабирования, персональный онбординг, договорные тарифы только в портале как стимул |
| Просадка SEO после смены URL | среднее | полная карта 301, поэтапный запуск, мониторинг 8 недель, сохранение структуры ключевых страниц |
| Отсутствие качественного фотоконтента | среднее | заложить фотосессию парка и объектов в этап 0 |
| Платёжный шлюз: задержки подключения (KYC банка) | среднее | начать оформление на этапе 1, предусмотреть «оплата по счёту» как fallback |
| Сезонность строительства — пик нагрузки весна–осень | низкое | нагрузочное тестирование, автоскейлинг воркеров |

**Допущения:** заказчик выделяет ответственного за контент и главного инженера для верификации технических данных; фирменный стиль предоставляется или разрабатывается отдельно; доступ к старой БД сайта предоставляется; существующая учётная система документирована для интеграции фазы 2.

# Приложение Г. Основные пользовательские истории (выдержка)

**B2C**
- Как владелец частного дома, я хочу описать «поднять бытовку 3 т на участок за забором», чтобы система сама подобрала кран и назвала цену, потому что я не знаю, что такое вылет стрелы.

**B2B**
- Как прораб, я хочу создать заявку на кран на вторник 8:00 за 30 секунд из шаблона прошлой недели.
- Как прораб, я хочу отметить на плане объекта точку стоянки крана, чтобы водитель не искал въезд и не терял час.
- Как прораб, я хочу подтвердить или оспорить сменный рапорт в день смены, чтобы в конце месяца не было спора о часах.
- Как снабженец, я хочу видеть свои договорные ставки и текущий баланс, чтобы планировать бюджет объекта.
- Как руководитель, я хочу отчёт по расходам на технику по каждому объекту за квартал в XLSX.
- Как ИТ-специалист партнёра, я хочу через API автоматически создавать заявки из нашей системы планирования.

**Бэкофис**
- Как диспетчер, я хочу видеть все заявки и весь парк на одном экране с подсветкой конфликтов, чтобы распределять технику за минуты, а не за часы.
